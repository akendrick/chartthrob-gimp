# ChartThrob → GIMP Port: Project Outline & Implementation Plan

Source reference: https://github.com/joker-b/ChartThrob (`ChartThrob.jsx`, v1.15, 2019).
Target: a GIMP plugin providing equivalent chart-generation and scan-analysis workflows.

---

## 1. Project Outline

### 1.1 Goals

- **G1 — Functional parity.** Reproduce both ChartThrob workflows: (a) generate a printable
  grayscale calibration chart, (b) analyze a scanned print of that chart and produce a
  tone-correction curve.
- **G2 — Algorithmic fidelity.** Port the core math (paper-tone normalization, dynamic-range
  detection, monotonic curve-point interpolation) exactly, so outputs are numerically
  verifiable against the original algorithm, not just "similar-looking."
- **G3 — Native GIMP implementation.** Use GIMP's real public API (direct gradient fill,
  direct histogram/pixel reads, native curves) instead of replicating Photoshop's
  `ActionDescriptor`/`executeAction` workarounds, which exist only because PS's scripting DOM
  lacks public calls for those operations.
- **G4 — Cross-platform.** One code path for Windows/Mac/Linux (GIMP's PDB is uniform across
  platforms; the original's install instructions had OS-specific folder notes that we don't need).
- **G5 — Testability.** Every piece of core logic must be unit-testable without a running GIMP
  instance, plus have a headless integration-test path runnable in GIMP's batch mode.
- **G6 — No legacy cruft.** Drop the Google Analytics Measurement Protocol v1 telemetry
  (`GaEmitter` in `ChartThrob.jsx`, and the dead duplicate `ps2ga.jsx`) entirely — it's a
  sunset protocol and shouldn't be reintroduced silently in a rewrite anyway.
- **G7 — Third-party-AI reviewable.** Clear module boundaries, type-annotated signatures, and
  docstrings on non-obvious invariants, so another AI (or human) reviewer can audit the port
  function-by-function against the original without re-deriving the math from scratch.

### 1.2 Non-Goals

- Pixel-identical recreation of Photoshop's ScriptUI dialog layout — use GIMP-idiomatic dialogs.
- Support for GIMP versions without GEGL (i.e., pre-2.10).
- Any phone-home telemetry.
- New features beyond ChartThrob 1.15's scope (extra chart sizes, non-grayscale processes,
  etc.) — that's a v2 discussion, out of scope here.

### 1.3 Success Criteria

| # | Criterion |
|---|---|
| SC1 | Given a chart generated by the tool, plus a synthetically-distorted "scan" of it (a known, deliberately non-linear transfer function applied in test code), the recovered correction curve — when composed with the known distortion — is monotonic and flattens tonal response within an agreed tolerance. **Verified against real GIMP 3.2.4** (see `tests/integration/manual_full_roundtrip.py`): a nontrivial 5-point synthetic distortion reconstructs to within 1/255 at most of the 14 control points, up to ~7/255 at one point near the top of the range, from compounding two independent 14-point smooth-spline fits (the injected distortion and the recovered correction) on top of 101-patch quantization. The original ≤2/255 figure here was an untested planning-time guess; ≤8/255 is the empirically-grounded tolerance now asserted in that test. This is the automated proof that "the math still works." |
| SC2 | Generated chart geometry (patch positions/sizes, strip counts) matches the original's layout formulas 1:1 at a given DPI, verified by comparing computed coordinates (not rendered pixels). |
| SC3 | Every edge case the original explicitly guards against (blank/inverted scan, non-RGB mode, too-small crop, degenerate dynamic range) produces an equivalent user-facing error/warning, never a crash. |
| SC4 | 100% of ported pure-logic functions have unit tests with ≥90% branch coverage. |
| SC5 | The plugin installs and runs end-to-end in a real GIMP session for both workflows, no manual patching. |

2. Port chart-generation workflow

4. UI layer & plugin registration

## 2. Implementation Plan

### 2.0 Target Environment (assumption — flag if this should change)

Primary target: **GIMP 3.0.x**, Python 3, via GObject-Introspection (`gi.repository.Gimp`),
registered as a `Gimp.PlugIn` subclass. GIMP 2.10's Python-Fu (Python 2) is legacy; if broader
2.10 compatibility is required later, the pure-logic layer (Phase 1) is Python-version-agnostic
and only Phases 2–4 (GIMP calls, plugin registration) would need a parallel 2.10 code path.

why these are manual scripts rather than the originally-planned
`headless_harness.py` + pytest-collected `test_full_roundtrip.py`.

### 2.2 Phase 1 — Pure Math/Logic Layer (no GIMP dependency)

Port function-by-function, preserving exact algorithm and edge-case behavior.

| Original (`ChartThrob.jsx`) | Ported to | Notes |
|---|---|---|
| `toGray(C)` | `curve_math.to_gray(rgb) -> float` | Keep the simple average (not the commented-out luminance-weighted variant) — this is a *deliberate* preserved behavior, document it as such rather than "fixing" it. |
| `grayValues(ColorSamples)` | `curve_math.normalize_paper_tone(samples) -> list[float]` | Divide by paper color (sample 0), clamp each channel to 255, surface the "unusually dark — possibly scanned a negative" warning as a return flag rather than an `alert()`. |
| `determineDynamicRange(GraySamples)` | `curve_math.compute_dynamic_range(values) -> DynamicRange` (dataclass: `normalized, min, max, min_idx, max_idx, degenerate: bool`) | Preserve the `dR < 1` degenerate fallback to a linear ramp. |
| `findValueThatGives(origValue, normalizedSamples)` | `curve_math.find_value_for(orig_value, normalized_samples) -> float \| None` | Preserve the inverse-interpolation algorithm exactly, including the `origValue == 0` special case and both "sample values start above/never reach" boundary conditions — return `None` instead of `alert()`-and-`-1`. |
| `verifyCurve(curvePoints)` | `curve_math.verify_curve(points) -> bool` | Return bool instead of alert+return code. |
| negate logic inside `verifyCurve` | `curve_math.negate_curve(points) -> list[point]` | Split out as its own function (`255 - v` per point) so it's independently testable. |
| `patchCenter`, `selectPatch` math, `boundArray`, `gX21`/`gXGrad`/`gXBar`, `resetDpi` | `geometry.ChartLayout` dataclass, built from a DPI value; `geometry.patch_center(layout, i, j)`, `geometry.patch_bounds(layout, i, j)` | Replace the globals (`gWidth`, `gPatch`, etc.) with an explicit, constructed, immutable layout object. |

**Exit criteria:** all functions above exist with type hints, docstrings on non-obvious
invariants, and passing unit tests (see 2.6).

### 2.4 Phase 3 — Scan Analyzer (GIMP calls) — ✅ DONE, see API_MAPPING.md

Built largely as planned, with the open technical spike now resolved:
**`curveLayer` → `Gimp.DrawableFilter` running the `"gimp:curves"`
operation**, attached non-destructively via `append_filter()` and hidden by
default. This was *not* the first thing tried — see 3.2 for why the more
obvious-looking `Drawable.curves_spline()`/`curves_explicit()` calls were
ruled out (deprecated, and confirmed to silently no-op for any curve with
more than two control points in GIMP 3.2.4, which would have been a subtle,
almost-invisible correctness failure for a tool that always needs up to 14
points). `chart_analyzer.analyze_chart(image, options)`'s actual signature
takes just `image` and a `ScanOptions` dataclass, not a separate `layout`
parameter as sketched here originally — the analyzer derives its own
sampling geometry from the image's actual pixel dimensions
(`geometry.patch_center`/`patch_sample_bounds`), since a scanned image's
size has no necessary relationship to whatever DPI the original chart was
built at. `scanResultsReport` maps to `plugin.py`'s `_report_message()`, not
its own dialog — see Phase 4 below. Full current table in
`API_MAPPING.md`'s Phase 3 section.

**Exit criteria:** ✅ met — headless round-trip test passes SC1 (see 3.2 and
`tests/integration/manual_full_roundtrip.py`).

### 2.5 Phase 4 — UI / Plugin Registration — ✅ DONE, see API_MAPPING.md

Built as **two** separate `Gimp.PlugIn` procedures (`python-fu-chartthrob-build`,
a plain `Gimp.Procedure`; `python-fu-chartthrob-analyze`, a `Gimp.ImageProcedure`)
rather than one adaptive dialog mirroring `userDialog()`'s single-window
shape — still "mirroring the choice" as originally worded here, just as two
GIMP-idiomatic menu commands instead of one dialog that reshapes itself.
GIMP's own menu-sensitivity system (`ProcedureSensitivityMask.DRAWABLE`)
replaces the original's manual "is a document open" check for free.
Dropped from the parameter set during implementation, both for concrete
reasons (not oversights): **chart name** (`gChartName`) — nothing to wire it
to without a "Save As" step, which stayed out of scope; **Excessive
Messages** (`gNoisy`) — its only original effect was extra debug `alert()`
popups, superseded by this port's actual unit test suite. `helpDialog()`'s
step list became each procedure's long-form `set_documentation()` blurb,
relying on GIMP's own Procedure Browser instead of a hand-built help
window (that gap only existed in the original because ScriptUI dialogs
have no built-in documentation display). No telemetry anywhere (G6) —
confirmed by inspection, there's no networking code in this port at all.

**Exit criteria:** ✅ met — SC5. Verified against a real, locally installed
GIMP 3.2.4: both procedures register with the PDB, the build procedure
runs end-to-end through a real PDB call, and the analyze procedure
correctly attaches its curve filter. See 3.2 and

## 3. Progress Log — Discoveries, Workarounds, and Next Steps

*(Added after Phase 4. Read this section for "what's the real current state,"

### 3.1 Where things stand

Phases 0–4 are complete and — unusually for a plan document — every one of
them has been **verified against a real, locally installed GIMP 3.2.4**,
not just written and assumed correct. That distinction matters: several of
the discoveries below would have shipped silently broken if verification
had stopped at "the code looks right" or "the code runs without raising."

- **60 unit + property tests, 100% line coverage** on the pure-logic layer
  (`chartthrob/geometry.py`, `chartthrob/curve_math.py`), runnable with
  plain `pytest` — no GIMP needed.
- **Six real bugs found in the GIMP-dependent layers** (plus one
  test-harness-only limitation that isn't a plugin defect), all invisible
  from code review and all caught only by checking actual numeric output
  against known ground truth, not by visual inspection or "it didn't
  crash." Full detail in 3.2.
- **The Phase 3 curve-representation spike is resolved**, and the
  resolution changed mid-flight based on evidence, not preference — see 3.2.
- **The plugin is installed and live** in the local GIMP install for
  testing: `plugin/chartthrob-plugin` is symlinked into
  `~/Library/Application Support/GIMP/3.2/plug-ins/chartthrob-plugin`. This
  is a real, user-visible change outside the repo, flagged here so it isn't
  a surprise; remove the symlink to undo it.
- **`plugin.py` moved out of the `chartthrob/` package**, unlike the
  original repository-layout sketch in 2.1. GIMP 3 discovers Python plugins
  by folder-name-matches-file-basename convention, which doesn't fit
  inside a regular installable Python package layout — so it now lives at
  `plugin/chartthrob-plugin/chartthrob-plugin.py` and imports the
  `chartthrob` package via a `sys.path` adjustment relative to its own
  (symlink-resolved) location.

### 3.2 Discoveries — bugs and quirks found during implementation

These are grouped by where they were found, in the order they were hit.
Every one is also documented in-line in `API_MAPPING.md` at its specific
function's row; this is the narrative version.

**In the original algorithm itself (preserved on purpose, not "fixed"):**
1. `verifyCurve`'s monotonicity check never updates its comparison
   baseline — it only verifies every curve point's x-value is ≥ the
   *first* point's x-value, not pairwise monotonicity against each
   preceding point. Reproduced exactly in `curve_math.verify_curve`, with
   a pinned regression test for the specific "rises then dips but stays
   above the first point" case that the original actually accepts.
2. Paper-tone normalization's zero-division has two different outcomes in
   JS depending on the *sample* value, not just the paper value:
   nonzero-over-zero → `Infinity` → clamped to 255 by the next line;
   zero-over-zero → `NaN`, which skips that same clamp (`NaN > 255` is
   `false` in JS). A naive port would have collapsed both cases to 255.
   `curve_math._normalize_channel` reproduces both outcomes distinctly.
3. `determineDynamicRange`'s degenerate-scan fallback ramps 0→255 by index
   position, the *opposite* direction from the normal case's 255→0
   (lightest-to-darkest) convention `find_value_for` expects. Practical
   consequence: a genuinely blank/flat scan likely still fails the
   separate "not enough valid curve points" check right after this
   fallback runs, rather than gracefully producing a usable pseudo-linear
   curve as the fallback's existence might suggest. Documented, not
   patched over — it's a property of the *original* algorithm.
4. `find_value_for` never clamps its output to [0, 255] — it will happily
   extrapolate outside that range given samples that don't span the full
   0–255 dynamic range. This never happens in the real pipeline (samples
   always come from `compute_dynamic_range`, which always spans exactly
   0–255 by construction) but a hypothesis-generated property test caught
   it immediately for narrower, unrealistic inputs — which is exactly what
   property testing is for. Documented as a stated precondition rather
   than defended against with an unnecessary clamp.

**Against real GIMP (Phase 2 — chart building):**
5. **Linear-vs-sRGB colorspace bug.** `Gegl.Color.set_rgba(v/255.0, ...)`
   sets values in *linear light*, not sRGB gamma-encoded — gray value 128
   was actually painting as ~188/255 when read back via
   `Drawable.histogram()`. Invisible at pure black/white (gamma curves are
   identity at both endpoints) and invisible by eye in a small PNG
   preview, which is exactly why it survived an initial visual check.
   Caught only once patch values were checked numerically. Fixed with
   `set_rgba_with_space()` + Babl's `"R'G'B'A float"` (explicitly
   gamma-encoded) format; verified to round-trip exactly (128 in → 128.00
   out).
6. **Brush-vs-line stroke bug.** `edit_stroke_selection()` strokes with the
   *active paint brush* by default (`Gimp.StrokeMethod.PAINT_METHOD`), not
   a plain vector line — `context_set_line_width(1.0)` alone was silently
   ignored, and the chart's border came out ~9px wide instead of 1px,
   swallowing the neighboring patch's edge and corrupting the very first
   thing Phase 3 samples (the paper-tone reference patch read as 173
   instead of 255). Fixed with
   `context_set_stroke_method(Gimp.StrokeMethod.LINE)` first. Found by the
   Phase 3 round-trip test, not by looking at the Phase 2 chart — the
   thick border is *visually obvious* in hindsight, but the first
   full-chart screenshot review didn't catch it because nothing was
   compared against a numeric expectation at the time.

**Against real GIMP (Phase 3 — scan analysis, the curve-representation spike):**
7. **`Drawable.curves_spline()`/`curves_explicit()` are deprecated *and*
   silently no-op for any curve with more than two control points** in
   GIMP 3.2.4 — confirmed directly: a 2-point curve applies correctly, a
   3-point or 14-point curve leaves the image completely unchanged, no
   error raised. This ruled out the most obvious-looking API outright,
   regardless of the deprecation notice, since the real curve always has
   up to 14 points. Resolved by using `Gimp.DrawableFilter` running the
   `"gimp:curves"` operation instead (the deprecation notice's own
   recommended replacement), attached via `append_filter()` and hidden by
   default — confirmed correct for both a 3-point and a 14-point curve via
   exact histogram-mean checks.

**Against real GIMP (Phase 4 — plugin registration):**
8. **Babl/Gegl lazy-initialization requirement.** `Babl.format(...)` at
   module import time crashes ("you must call babl_init first") during
   GIMP's plugin *query* phase — the lightweight subprocess GIMP uses at
   startup to enumerate a plugin's procedures, which doesn't fully
   initialize babl/Gegl the way the *run* phase does. This never showed up
   in ad hoc batch-console testing, because those scripts run inside an
   already-fully-initialized GIMP process. Fixed by making the sRGB format
   lookup lazy (resolved and cached on first real use) in both
   `chart_builder.py` and `chart_analyzer.py`.
9. **`Gimp.Display.new()` raises when there's no display server** to
   attach a window to (headless/batch invocation) — wrapped in a
   `try/except TypeError` in `build_chart_run`, since the image is still
   created and valid regardless; a real interactive GIMP session never
   hits this path.
10. **Bare module-level `Gimp.main(...)` blocks forever if imported**
    instead of run directly — hung on `Gimp.main()`'s wire-protocol
    handshake when a test harness imported the plugin file as a module.
    Fixed with the standard `if __name__ == "__main__":` guard, which is a
    no-op for real usage (GIMP always invokes plugin files directly, so
    `__name__` is always `"__main__"` in that path).
11. **GI-binding harness limitation (not a plugin defect):** GIMP 3.2.4's
    Python bindings don't support setting a `GimpCoreObjectArray`-typed
    `ProcedureConfig` property (the implicit "drawables" argument every
    `ImageProcedure` has) via generic `set_property()` — confirmed with
    both a list and a tuple, identical `TypeError` either way. This blocks
    driving the analyze procedure through a *fully* PDB-marshaled call in
    a headless script. It does not affect real usage: GIMP's own menu
    dispatch supplies `image`/`drawables` as native arguments directly,
    the same way `foggify.py` (bundled with GIMP, used as a reference
    pattern) receives them. Worked around in
    `tests/integration/manual_plugin_e2e.py` by calling the real
    `analyze_scan_run()` function directly with a real image/drawable and
    a minimal stand-in config object, rather than skipping the check or
    reimplementing the function under test.

**Architecture change made during Phase 5, in service of testability
(G5), not a bug fix:**
12. `chart_analyzer.analyze_chart()`'s post-sampling orchestration
    (normalize → dynamic range → 14-point curve loop → verify → negate)
    was originally inlined directly in that function — meaning it lived in
    a module that imports `gi`/`Gimp` at the top level, so it could never
    be unit-tested without a full GIMP install, even though none of that
    logic actually touches GIMP. Extracted into
    `curve_math.build_curve_from_samples()` (Phase 1, GIMP-free) once
    writing the Phase 5 golden/stress suites made that limitation concrete
    rather than theoretical. Re-verified behavior-preserving by re-running
    `manual_full_roundtrip.py` and `manual_plugin_e2e.py` against real GIMP
    after the refactor — identical results both times.

**Two more findings, surfaced only by actually running the Phase 5 stress
suite against real code rather than trusting the original table's guesses:**
13. **A single corrupted/clipped patch distorts roughly half the recovered
    curve, silently.** The `clipped_patch_scan` golden fixture (one patch
    forced to a dust-speck-like 0 in the middle of an otherwise-clean ramp)
    doesn't error — `verify_curve` only checks x-values, which are
    untouched — but the clipped value becomes `compute_dynamic_range`'s new
    recorded minimum, breaking the monotonic-descending-samples assumption
    `find_value_for` relies on. Concretely: `x=0.0` drops out of the curve
    entirely, and the y-values for roughly the first half of the input
    range collapse to a narrow, substantively wrong band instead of
    tracking x. This is a faithfully-preserved fragility in the *original*
    algorithm, not a defect introduced by this port — but it was
    theoretical until this fixture made it concrete and numeric. See
    `tests/golden/generate_fixtures.py`'s `clipped_patch_scan` description.
14. **Stress-test case 10 ("non-monotonic curve points caught by
    `verify_curve`") is provably unreachable via the real pipeline.**
    `build_curve_from_samples`'s curve-point x-values are always
    `round_half_up(255*j/13)` for a fixed `j` in `range(14)`, filtered but
    never reordered — so they're always strictly increasing regardless of
    how corrupted the input samples are, and the `verify_curve` check
    inside `build_curve_from_samples` can never actually return `False`
    there. Marked `# pragma: no cover` with the proof inline, the same
    treatment already given to `find_value_for`'s `delta == 0` dead branch
    in Phase 1. `verify_curve` itself remains directly reachable and
    tested standalone (a hand-built `curvePoints` list, not one built by
    this pipeline) — only this *specific call site* can't trigger it.

## 4. GIMP Platform Gaps & Ecosystem Opportunities

Everything below is written from the workarounds already catalogued in 3.2
— the question here is which of those are worth pushing back upstream
(making GIMP itself better, not just working around it), and whether
anything already in the GIMP ecosystem could close a gap instead of us
maintaining a workaround indefinitely. Where a claim isn't independently
verified against real GIMP the way the rest of this document insists on,
that's called out explicitly rather than stated as fact.

### 4.1 Worth filing upstream against GIMP itself

1. **`Drawable.curves_spline()`/`curves_explicit()` silently no-op past two
   control points** (3.2 item 7). This is the most serious one to report:
   a *deprecated-but-still-shipped* PDB call quietly doing nothing for
   inputs beyond its apparent working range, with no error, is worse than
   either removing it outright or having it raise. Confirmed directly
   (2-point curve: applies; 3-point and 14-point curves: silent no-op) —
   worth a GIMP GitLab issue with that minimal repro, since anyone else
   who reaches for the more obvious-looking `curves_spline` over
   `Gimp.DrawableFilter`+`"gimp:curves"` will hit this identically.
2. **`edit_stroke_selection()`'s brush-vs-line default is a silent
   footgun** (3.2 item 6): calling `context_set_line_width()` without also
   calling `context_set_stroke_method(Gimp.StrokeMethod.LINE)` first does
   nothing detectable — no warning, no error, just a stroke that ignores
   the width you just set. A one-line addition to
   `context_set_line_width()`'s docstring (or a runtime warning when line
   properties are set while the stroke method is still
   `PAINT_METHOD`) would have saved the debugging time this took here.
3. **Babl/Gegl aren't initialized during a plugin's query phase**
   (3.2 item 8): `Babl.format(...)` at module scope crashes with "you must
   call babl_init first" specifically when GIMP is enumerating a plugin's
   procedures at startup, not when it's actually running one. `foggify.py`
   (bundled with GIMP) works around this itself with an explicit
   `Gegl.init(None)` inside `do_create_procedure()` — but that workaround
   is only discoverable by reading a bundled example's source, not
   documented anywhere obvious. Either GIMP could initialize babl/gegl
   before the query phase runs plugin code at all, or this requirement
   belongs explicitly in the `Gimp.PlugIn` API docs.
4. **`GimpCoreObjectArray`-typed `ProcedureConfig` properties (the
   implicit "drawables" argument on every `ImageProcedure`) can't be set
   via generic `set_property()`** (3.2 item 11) — confirmed with both a
   Python list and a tuple, identical `TypeError` either way. This is a
   gap in the Python bindings specifically, not core GIMP; worth reporting
   against `gimp-python`/PyGObject bindings, since it blocks anyone trying
   to drive an `ImageProcedure` headlessly (batch scripting, automated
   testing, CI) without a real GUI supplying those arguments natively.
5. **GIMP's own bundled example plugins don't guard their `Gimp.main()`
   call** — `foggify.py`, `gradients-save-as-css.py`, and every other
   bundled example end with a bare
   `Gimp.main(SomeClass.__gtype__, sys.argv)` at module scope, not behind
   `if __name__ == "__main__":`. That's a no-op difference for how GIMP
   itself invokes them, but it's a footgun for anyone who later wants to
   unit-test or import their own plugin module the way this project's
   `manual_plugin_e2e.py` does (3.2 item 10) — worth suggesting as a
   template fix in GIMP's own example plugins, so the fix propagates to
   everyone who copies them as a starting point (as this project did).
6. **No scriptable way to save or load a curve.** `Gimp.Curve` has
   `add_point`/`clear_points`/`get_point`/etc. but no `export`/`import` or
   file-based save/load of any kind — confirmed by listing every method on
   the class directly. A broader search for anything named `*preset*`
   anywhere in the entire `Gimp-3.0` GI typelib returned nothing at all,
   confirming there's no generic tool-preset save/load exposed to
   scripting either (whatever GIMP's Curves dialog itself may or may not
   offer through its GUI — see 4.3). This is the single biggest concrete
   feature gap relative to Photoshop's draggable, savable curve layers,
   and the most valuable one to file as a feature request:
   `Gimp.Curve.export_to_file()`/`import_from_file()` (or a generic
   curve-preset PDB call) would directly replace this project's own ad hoc
   JSON save/load format (Phase 6) with something GIMP-native and
   presumably GUI-compatible too.

### 4.2 A capability confirmed during this session, worth using more directly

Verified empirically (see `tests/integration/manual_curve_reuse_probe.py`): a single
`Gimp.Curve` object can be attached to separate `Gimp.DrawableFilter`s on
*different* images within the same GIMP session and produces identical
results both times (128→200 exactly, on two independently created test
images). That means "apply this same curve to another image" doesn't
strictly require a save/reload round-trip when the target images are
already open in the same running session — only cross-session persistence
(closing GIMP, reopening later) genuinely has no native answer, per 4.1
item 6.

Practical follow-up for Phase 6: `chart_analyzer.apply_curve_to_drawable()`
currently rebuilds a fresh `Gimp.Curve` from a raw point list on every
call. It could instead optionally accept (and return) a `Gimp.Curve`
object directly, so a caller analyzing one chart and wanting to apply the
result to several already-open images in the same session can reuse the
same object rather than re-encoding points each time. The JSON save/load
plan remains the right answer for the cross-session case specifically —
this doesn't replace that, it just avoids over-using it for a same-session
case that already works natively.

### 4.3 Could other GIMP-ecosystem tools help?

- **G'MIC** (GREYC's Magic for Image Computing, shipped as the G'MIC-Qt
  plugin) is real, well-known, and actively maintained, and includes its
  own extensive curve/LUT/tone-mapping operations. It's a plausible
  fallback backend if `gimp:curves` (4.1 item 1's replacement path) ever
  proves insufficient for some future need — but it's an external
  dependency this project doesn't currently need, so only worth adopting
  if a concrete limitation in GIMP's own curves filter actually surfaces.
- **GIMP's Curves dialog may have its own GUI-level preset import/export**
  independent of anything exposed to scripting — **not verified in this
  session**, and per 4.1 item 6, nothing scriptable backs it even if the
  GUI feature exists. Worth checking by hand in the GIMP GUI before
  relying on any claim about it either way.
- **Existing digital-negative/step-wedge calibration scripts elsewhere in
  the GIMP community** — plausible that something similar exists (GIMP has
  a long Script-Fu history), but this hasn't been searched for and nothing
  specific is confirmed. If searching later (GIMP's old plugin-registry
  archives, PyPI's `gimp-plugin` adjacent packages, GitHub topics), treat
  any hit as a Script-Fu/Scheme tool more likely than a modern Python-GI
  one, given how long this niche has existed relative to GIMP 3's Python
  bindings.
- **External, non-GIMP interoperability** — the original ChartThrob already
  gestures at this via its "negate for QuadToneRIP" option. Both
  QuadToneRIP and ArgyllCMS have their own curve/profile file formats; if
  real interoperability with either is ever wanted, Phase 6's curve
  save/load format should target one of *their* formats instead of an ad
  hoc JSON, so a curve produced here can feed directly into an existing
  printing pipeline rather than requiring a manual re-entry step.
